# Travel View Native

A new Swift and SwiftUI app for iPhone, iPad, and Mac. Its shared `TravelCore` package uses SQLite through GRDB 7.12.0.

Open `Travel View Native.xcodeproj`, choose the **Travel View Native** scheme, select an iPhone simulator or **My Mac**, and press **⌘R**. Xcode downloads the pinned GRDB dependency on the first build. Physical iPhone installation requires selecting your Apple development team under **Signing & Capabilities**.

## Current native version

- **Upcoming** includes trips happening now, future trips, and plans with undecided dates. **All trips** also retains completed trips.
- **New trip** collects a name, destinations, optional dates, planned traveler count, optional USD budget, and notes. Dates are calendar days, and budgets are stored in whole cents.
- **Overview** displays saved trip details, notes, and the itinerary, and opens **Edit trip**. A failed save keeps the form open with the draft.
- **Planning overview** counts whole flights, stays, and activities, with totals for Idea, Planned, and Booked. Tap a booking-state total to browse those plans, or the dates shortcut to see plans with neither a start nor an end date. A flight's departure/arrival and a stay's check-in/check-out each belong to one plan and do not inflate these counts.
- **Find a plan** opens a separate browser for the current trip. Search saved titles, locations, notes, confirmation/booking references, flight numbers, airlines, and airport codes. Words can match different fields, and matching ignores case and accents. Combine search with type, booking-state, and Undated only filters. Reset restores all plans in the current trip; opening a result shows its usual detail page. Results and overview totals refresh after saved edits. Searches keep the complete day-by-day timeline and Coming up unchanged.
- **Day-by-day itinerary** groups plans by local calendar day. Flights show departure and arrival entries, stays show check-in and check-out, and activities can include optional start and end times. Undated plans have their own section at the end. Tap an entry to open its detail screen; editing either end of a flight or stay updates the same saved record.
- **Plan details** show the complete schedule, notes, booking state, and confirmation reference. Flights retain their existing booking-reference field; stays and activities have their own confirmation reference. Choose **Idea**, **Planned**, or **Booked** yourself in the editor. Existing items start as Planned, and neither a reference nor a provider lookup marks a plan as Booked. The timeline displays the saved state too.
- **Open in Maps** searches for the item's saved location or address. It appears when a location is present, opens only when tapped, and does not request the device's current location.
- **Coming up** previews today's scheduled entries or the next dated day, with a button that scrolls to it. The summary uses calendar days, and includes all of today's entries. It does not estimate which event happens next across different time zones. Its Today label follows the device's day and updates when the app becomes active, midnight passes, or the device time zone changes.
- **Flights** can be entered manually or selected by flight number and local departure date through the configurable flight service. Lookup results fill a reviewable draft. Flight clocks retain each airport's local time. The saved lookup is attributed and dated, with no automatic live-status refresh.
- **Check flight updates** is available in each flight entry's menu and its detail screen. Choose a matching schedule, compare Saved and Latest details, then save only the changes you select. Details that differ from the previous matching lookup stay unchecked. For manually entered flights without a comparable lookup, all replacements require selection. Title, notes, location, booking state and booking reference are kept. Missing provider values never clear known details. You can also save the lookup alone.
- **Share trip** in Overview opens a complete `.travelview` snapshot for someone with the app. It includes the trip, all itinerary items, dates, local times, notes, references, booking states, budget, traveler count and saved lookup snapshots. **Send trip** opens the native share sheet directly; **Save a copy** is optional. The screen explains how to open a received attachment and that no Travel View account is needed. Its complete-file contents are independent of the readable-text toggles.
- **Share readable itinerary** in the Share trip screen opens a text preview for someone without the app. Notes and booking/confirmation references are independently optional and start off each time the preview opens. **Share itinerary text** shares the preview text, and **Save text file** exports the same content as a UTF-8 `.txt` file. Times stay local to each location or airport, and personal details appear once per plan even when both ends of a flight or stay are shown. The text export uses current saved plans, excludes old provider snapshots, and leaves budget and traveler-count fields out.
- **Import shared trip** in the collection menu opens a received trip file. Files/Finder can also open the registered file type in Travel View. A pending-file banner offers **Review shared trip** so an open form can keep its draft. Review the snapshot, then import it as an independent trip. Existing trips are preserved. Reopening the same file offers the copy already imported, keeping its local edits and avoiding another duplicate. A newly prepared snapshot has a new file identity and imports as a separate manual copy.
- The collection’s **Trip files and backups** menu also exports a JSON backup or imports one. Backup import appends missing IDs and preserves the current details of existing IDs. An import can be retried safely.

The app has the bundle identifier `local.travelview.native`. Its database is `Travel View Native/trips.sqlite` inside its Application Support directory. On Mac, the app sandbox supplies that directory inside the app’s container. Numbered SQLite migrations add itinerary storage, optional local times, booking states and reservation references while preserving existing records. Version 4 JSON backups include the reservation fields and activity/stay times. Imports still accept version 1 trip-only backups, version 2 itineraries, and version 3 timed itineraries. Older items default to Planned with empty stay/activity references; existing flight references are retained. Limits are 10 MB, 5,000 trips and 25,000 itinerary records. Imports are atomic and keep existing records with matching IDs.

The shared text is a readable copy for use outside the app. Use the collection's JSON export when you need a backup that can be restored into Travel View. Sharing and saving a text copy do not change stored records. The complete trip-file import adds the receipt migration described below.

Trip files use the `travel-view-trip` version 1 format and the registered `local.travelview.trip` type, with a 10 MB limit. Import validates the same fields and relationships as a backup, creates new trip/item IDs, and preserves ordering when dates and times tie. A numbered migration adds `sharedTripImports`, a device-local receipt table that maps a file identity to its imported copy. The trip, items and receipt commit together. Receipts survive app restarts but are not included in version 4 backups; after restoring a backup on another device, importing a previously received file there can create another copy. Neither backups nor text exports are accepted as trip files.

For a manual transfer, use **Send trip → AirDrop, Messages or Mail**, then open the received attachment with Travel View and review/import it. Saving it into Files and finding it again in the app's import picker is a fallback. The operating system controls the receiving destination: [Apple notes](https://support.apple.com/guide/iphone/iphcd8b9f0af/ios) that AirDrop can save items into Files on iPhone or Downloads on Mac. On Mac, open that downloaded file (or use **Open With → Travel View**); on iPhone, use an attachment's available open/share options to choose Travel View. This does not require Travel View accounts or synchronization.

Within each day, entries with known times appear first in local clock order, followed by entries whose times are undecided. Same-day activities show a time range in one entry; an activity ending on a later date has an end entry on that date. A stay only generates check-in and check-out entries, so a long date range does not create empty days. These are views of the saved items, rather than extra records in the database.

Flight lookup needs the companion [flight service](FlightService/README.md). That guide covers direct AeroDataBox access, the optional existing API.Market gateway, and a no-key sample service. Manual flight entry works before the service is connected.

To follow **Save trip**, start at `save()` in `TripEditor.swift`. The form creates a `TripInput`, the store asks the repository to validate and commit it, and the returned `Trip` updates the collection and Overview. The form keeps a stable trip ID for save retries.

To follow **Open plan details**, start at the `NavigationLink` in `ItineraryDayView.swift` or `ItineraryBrowserView.swift`. It carries the trip and item IDs to a destination registered by `TripLibraryView`, which opens `ItineraryDetailView`. The detail page reads the current item from `TripStore`, so saving an edit refreshes the page without passing an outdated record back through navigation. Both ends of a stay or flight carry the same item ID.

To follow **Find a plan**, start at `PlanningSummaryView`. Its links carry a trip ID and optional initial filters to `ItineraryBrowserView`. The browser asks `TripStore` for that trip's records, then `ItineraryQuery` applies all selected filters and matches every search word against current saved fields. Older provider snapshot fields are excluded. Search returns each record once in the existing date/time order, with undated plans last. Query state stays in the browser while visiting details and resets when a new browser is opened. This feature changes no stored records or backup fields and requires no database migration.

To follow **Share trip**, start at the Overview toolbar, which opens `ShareTripFileView` directly. That view prepares one complete snapshot and gives it to the system share sheet through `ShareLink`. Saving a copy is a separate optional action. Platform-specific receiving help explains how to open an attachment instead of manually finding it again in the import picker.

To follow **Share readable itinerary**, use the secondary action in the Share trip screen. `ItineraryShareView` reads the current saved trip and asks `ItineraryText` to generate the same local-day entries used by the timeline. It filters by the trip ID again inside the generator. Both optional-detail choices live only in this sheet. `ShareLink` receives the generated text; Save captures a copy in `ItineraryTextDocument` before opening the file picker, so a later edit in another window cannot change an export already being saved. Text sharing does not upload or synchronize the trip in the background.

To follow **Import shared trip**, start at `readSharedTrip(from:)` in `TripLibraryView`. Both the native picker and `onOpenURL` enter this path. The file is read off the main actor while security-scoped access is active, then decoded and validated before a review can be opened. `TripStore.importSharedTrip` publishes the returned database snapshot only after the repository transaction commits. Receipts are checked inside that transaction too, so two windows importing the same file cannot create two copies. File sharing uses the complete snapshot captured when its preparation screen opens. Temporary file attachments are scoped to the app's temporary directory; later shares clean up attachments older than one day.

To follow **Check flight updates**, start at the flight entry menu in `ItineraryDayView.swift` or the detail page's actions menu. `FlightUpdateView` requests a schedule through the existing lookup screen, then `FlightUpdate` compares it with the saved plan and its previous lookup. The repository checks that the reviewed record is still current inside the save transaction. A review of an edited or deleted flight cannot overwrite newer changes or recreate a deleted record. The dated lookup remains part of `FlightDetails`; the separate reservation migration adds the user-owned booking state and stay/activity reference columns.

## Verification

From the repository root, run `swift test --package-path Native/TravelCore`. The 56 tests cover calendar days, exact money, persistence and save retries, Upcoming filtering, database upgrades, trip-scoped itinerary writes, date-line crossings, old/new backup imports and rollback, reviewed flight details and their source snapshot, day grouping and ordering, local time validation, Coming up selection, flight client responses, selected schedule updates, missing provider data, manual-edit preservation, reservation validation and persistence, legacy reservation defaults, Maps URL escaping, combined itinerary queries, accent/case matching, current versus old provider fields, stable search ordering, undated filtering, whole-plan counts, and readable itinerary exports. Complete-file tests cover full data round trips, format/size/relationship validation, independent identities, ordering, reopening and retaining edits, concurrent imports, rollback/retry, and migration from the preceding schema. Stale flight reviews are rejected even if only the booking state changed. The unchanged service has its own type check and six tests.

On November 13, 2026, all 36 core tests passed, and the app compiled for Mac, iOS Simulator and physical iOS devices (the device check used unsigned compilation). Isolated Mac and iPhone simulator apps verified detail navigation, saved references and state, immediate updates after editing, and returning from details through Overview to the trip collection. Both check-in and check-out opened the same stay. The Mac Maps action opened South Bank, London. A version 3 backup imported five items with their times, and a version 4 export retained the new references and states. Actual device installation was not part of this check.

On November 14, 2026, all 42 core tests passed. Mac, iOS Simulator and unsigned physical-device builds passed for the planning overview and browser. Isolated Mac and iPhone simulator checks covered state and undated shortcuts, reference searches, combined filters, no-result/reset behavior, opening details and returning with the query retained, and updated search results after an edit. On iPhone, changing an activity from Idea to Booked updated the overview to three booked plans. A separate empty Mac test trip showed zero plans and no records from the populated trip. Actual physical-device installation was not part of this check.

The sharing milestone on November 14, 2026 passed all 48 core tests and Mac, iOS Simulator and unsigned physical-device compilation. Isolated Mac and iPhone simulator apps verified the preview, optional-detail toggles, native share interfaces, and saving `.txt` files through their native file pickers. The saved UTF-8 files were read back to verify local schedules, excluded default notes/references, and optional references appearing once per plan. Reopening the Mac preview reset both options to off. Share interfaces were closed without sending a message. Actual physical-device installation was not part of this check.

The complete trip-file milestone on November 14, 2026 passed all 56 core tests and Mac, iOS Simulator and unsigned physical-device compilation. Isolated Mac and iPhone simulator apps verified complete-file preparation, native file sharing/saving, review and independent-copy import, and reopening the same file without another duplicate. A five-plan Mac export opened on the iPhone simulator with its local schedules, references, notes, budget and traveler count. Database checks confirmed new identities and preserved original records. The iPhone share sheet also saved a `.travelview` attachment whose complete JSON contents were read back. The subsequent sharing usability pass on November 14, 2026 compiled for Mac, iOS Simulator and unsigned physical iPhone targets. Isolated Mac and iPhone simulator checks verified that Overview opens complete-trip sharing directly, Send trip is primary, Save a copy is secondary, receiving help matches each platform, and readable text sharing remains accessible with its optional details initially off. The Mac Send trip action offered AirDrop, Mail and Messages; the text export still opened its native save dialog. Share/save dialogs were dismissed without sending messages. The user also reported successful complete-trip transfers between their Mac and physical iPhone using the preceding build.

For isolated interface testing, a Debug build accepts the `TRAVEL_VIEW_NATIVE_DATA_DIR` environment variable in its Run scheme. Choose a directory the app can access. On Mac, the sandbox permits a temporary directory inside the app's own container; an arbitrary folder under `/private/tmp` is outside that sandbox.

When installing a separate simulator QA app, set `PRODUCT_BUNDLE_IDENTIFIER` in the Xcode build (for example, `PRODUCT_BUNDLE_IDENTIFIER=local.travelview.native.detailsqa`). Keep that identifier consistent with the built app's signature and scene configuration. Editing only the finished app's `Info.plist` can make Files bring the app forward without delivering the file to its SwiftUI handler.

## Later features remain accounted for

The intended product split is free manual trip-file sharing/import and a future paid subscription for automatic synchronization and collaborative editing. Saved trips should remain readable/editable and manually shareable after a subscription ends. Accounts, synchronization and billing are not implemented in this milestone. Manual imports are independent snapshots; changing either person's copy does not update the other.

Expenses and individual travelers remain planned. They are not implemented in this milestone. A stable trip ID owns each itinerary item, and each item has its own stable ID. Future expense records and traveler participation can reference those identities without changing saved flight, lodging, or activity records. The current planned traveler count is a planning estimate; it does not stand in for future traveler profiles or assignments. The current USD budget remains a trip-level estimate, separate from future actual expenses.

When those features are added, the overview can derive totals and participation from their records. Further numbered migrations and backup versions will introduce their tables and relationships. No unused expense or traveler tables are created now.
